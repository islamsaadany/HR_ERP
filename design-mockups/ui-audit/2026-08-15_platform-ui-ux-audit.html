Findings

Ordered by how much they cost the team day to day.

F1 ✓ The same amount of money renders differently depending on the browser High

The egp() formatter is copy-pasted into eight files, in three different behaviours: some round, some don't; some pin the locale to en-US, most leave it to the browser.

BenefitsBoard.tsx:12 "EGP " + Math.round(n).toLocaleString() → rounds, browser locale PaymentsQueue.tsx:17 "EGP " + n.toLocaleString("en-US") → no rounding, pinned admin/benefits/page.tsx:33 "EGP " + n.toLocaleString() → no rounding, browser locale email/templates.ts:14 "EGP " + n.toLocaleString("en-US") → no rounding, pinned …plus ResetBenefitsCard, ManualReleaseForm, ReimbursedCell, BenefitsOrientation, ReleaseManager

Two consequences, both verified by running the code. A figure of 45,000.5 shows as EGP 45,001 on the benefits page but EGP 45,000.5 on the Finance queue. More importantly, toLocaleString() with no locale follows the viewer's browser — and on an Arabic-locale browser, which is entirely normal in Cairo, it renders EGP ٤٥٬٠٠٠. So an employee could see Eastern Arabic numerals in the app and Western numerals in the very same claim's email. For the one module that handles money, that reads as a bug in the numbers themselves.

Fix: one shared formatEGP() in src/lib/labels.ts (beside the existing formatDate, which already pins en-GB and is the model to follow), locale pinned, one rounding rule. Replace all eight copies. No visual change on an English browser — this only stops the drift.
F2 ✓ Delete buttons destroy authored content on a single click High

Handbook sections, handbook resources, knowledge articles, announcements, onboarding activities and a medical commitment can all be deleted with one click and no confirmation.

admin/handbook/page.tsx:45 Delete section — no confirm admin/handbook/page.tsx:73 Delete resource — no confirm admin/knowledge/page.tsx:135 Delete article — no confirm admin/announcements/page.tsx:44 Delete — no confirm admin/onboarding/page.tsx:55 Delete activity — no confirm admin/benefits/page.tsx:358 Remove medical — no confirm DepartmentsManager.tsx:69 confirm("Remove …? This can't be undone.") ← the right pattern RegistryHeader.tsx:142 confirm(…) ← already does it

A knowledge article is a long authored piece; a handbook section is company policy. These sit next to an "Edit" link, in a list, at small text size — a misclick is one pixel away and there is no undo. Two surfaces in the same admin area already confirm before destroying, so the inconsistency is an oversight rather than a decision.

Fix: reuse the existing confirm() pattern from DepartmentsManager.tsx:69, naming the item being deleted. Six one-line changes, no redesign.
F3 Almost no form label is actually attached to its field Medium

Across the app there are 106 <label> elements. Only 4 use htmlFor. Roughly nine more wrap a checkbox (which is fine). The rest sit as a sibling of the input, with nothing connecting them.

EmployeeForm.tsx:129 <label className={L}>Department</label> <select name="department" …> ← sibling, not associated Worst affected: EmployeeForm (22 labels) · ArticleForm (11) · ActivityForm (8) BenefitsBoard (7) · SectionForm (6) · PlanYearDialog (5)

Two practical effects. Clicking the word "Department" doesn't focus the field — a small daily friction on the longest form in the app, the employee record. And a screen reader announces those fields as unlabelled, so the HR employee form is close to unusable that way. It also makes the fields harder to hit on a phone, where the label is a much bigger tap target than the input.

Fix: add matching htmlFor/id pairs. Mechanical, but ~90 edits across ~20 files, so worth doing as its own pass. Nothing changes visually.
F4 Sorting a table column is impossible without a mouse Medium

In the employee registry and the benefits catalogue, sorting is an onClick on the <th> itself — no button, no tabIndex, no role, no key handler. Nothing focusable exists, so the keyboard can never trigger it.

EmployeeGrid.tsx:560 <th … onClick={() => onHeaderSort(col.key)}> no tabIndex/onKeyDown/role CatalogueGrid.tsx:225 <th … onClick={() => onHeaderSort(col.key)}> no tabIndex/onKeyDown/role DirectoryBrowser.tsx sorting is a real <button> ← the pattern to copy

The registry is the densest screen in the product and sorting is how you find anyone in it. Note the inline editing in these same grids is done properly with real <button> elements — so it's specifically the header that was missed.

Fix: wrap the header label in a <button type="button">, as the Team Directory already does. Drag-to-reorder stays mouse-only, which is acceptable for an enhancement. Also move aria-sort onto the <th> — in DirectoryBrowser.tsx:219 it currently sits on the button, where assistive tech ignores it.
F5 The medical-commitment modal isn't announced as a dialog and won't close on Escape Medium

Of six modals in the app, three declare role="dialog" and aria-modal. The three that don't include both modals in BenefitsBoard — the medical cover setup and the guaranteed-benefit claim.

BenefitsOrientation.tsx role=dialog ✓ PlanYearDialog.tsx role=dialog ✓ ManualReleaseModal.tsx role=dialog ✓ AddCatalogItemModal.tsx ✗ BenefitsBoard.tsx (MedicalModal, GuaranteedClaimModal) ✗ and no Escape handler

Committing medical cover is the single most consequential thing an employee does in this product — it's locked afterwards and only HR can change it. That modal has no focus trap, no Escape key, and screen-reader users aren't told a dialog opened. Its sibling modals in the same feature already do all three, so this is an inconsistency inside one module.

Fix: copy the semantics already used in BenefitsOrientation.tsx — role="dialog", aria-modal="true", a labelled title, and Escape-to-close. No visual change.
F6 On a phone, the pool balance is buried under every benefit row Medium

The benefits page is a two-column grid that collapses to one column below lg. The pool card is the second child, so on a phone it renders after the entire list of benefits.

BenefitsBoard.tsx:248 grid … lg:grid-cols-[1fr_320px] ├─ <div> benefit rows → first on mobile └─ <aside> pool meter → last on mobile, below everything PROJECT_DETAILS.md:81 "The live summary stays visible while scrolling — sticky panel on desktop, pinned floating bar on mobile"

"How much have I got left" is the context for every decision on that page, and on mobile you must scroll past all of it to find out. Worth flagging separately: the documented mobile behaviour — a pinned floating bar — no longer exists; it was lost in the spec-018 redesign and the docs were never updated. Per the constitution that's a documentation bug to report rather than quietly realign, so I've left the line alone pending your call.

Fix (needs a mockup first): either restore a compact pinned summary bar on mobile, or reorder so the pool card comes first on small screens and the sticky column keeps its place on desktop. The second is a one-line change; the first matches what the docs promise. Your call which — and either way the docs need correcting.
F7 Expandable rows in the incentive report are mouse-only Low

Two expandable sections are onClick handlers on a <tr>.

CycleReport.tsx:490 <tr className="cursor-pointer …" onClick={() => toggleComm(c.name)}> CycleReport.tsx:610 <tr className="cursor-pointer …" onClick={() => setSchemeOpen(…)}>

Same class of issue as F4, but on a screen used by two or three people rather than the whole company, which is why it's ranked lower.

Fix: make the first cell a real button, or give the row a button-like affordance.
F8 "Confirm payment" gives no sign it's working Low

The Finance confirm form has no pending state — the button doesn't disable or change label while the action runs.

PaymentsQueue.tsx:85 <button …>Confirm</button> no disabled / pending finance/actions.ts:47 if (!claim || claim.status !== "APPROVED") redirect(…) ← server guard

I checked whether this could double-pay: it can't. confirmPayment refuses anything not in APPROVED, so the second submission is rejected. The cost is confidence, not correctness — on a slow connection there's no feedback, and an impatient double-click produces "That claim isn't awaiting payment anymore", which reads like a failure when the payment actually succeeded.

Fix: use the useTransition pending pattern already used in BenefitsBoard's claim form ("Submitting…" + disabled).
F9 Two small consistency slips Low

The active sort caret in the employee registry is gold-600 on the navy header — 4.33:1, which clears AA for large text but not for the 10px it's actually set at. And PlanYearDialog formats dates itself rather than using the shared helper, so it shows "1 Jan 2026" where the rest of the app shows "01 Jan 2026".

EmployeeGrid.tsx:572 text-[10px] … text-gold-600 4.33:1 on navy-800 PlanYearDialog.tsx:27 toLocaleDateString("en-GB", { day: "numeric", … }) lib/labels.ts:73 formatDate() → { day: "2-digit", … } ← the shared one
Fix: move the caret to gold-300 (8.74:1, already used in the Team Directory after this week's fix) and point the dialog at formatDate.

Checked and cleared

Things I suspected, chased, and found were not defects. Recording them so nobody re-opens the same trail.

R1 Column headers turn invisible on hover Not a bug

Both grids put hover:text-navy-700 on a <th> whose background is navy-800 — a contrast ratio of 1.17:1, which would make the label vanish. It doesn't, because .ff-data-table thead th is declared outside any cascade layer in globals.css, and unlayered CSS beats Tailwind's @layer utilities regardless of specificity. I confirmed this in the built stylesheet rather than reasoning about it. The hover class is dead code — harmless, but worth deleting so it doesn't mislead the next person.

R2 Links opening in new tabs without rel="noopener" Not a bug

Four target="_blank" links looked bare on a line-by-line scan. All four carry rel="noopener noreferrer" on the following line.

R3 Images missing alt text Not a bug

Both raw <img> elements (the avatar and the business-unit logo) set alt correctly.

Suggestions

Not defects — things that would make the platform nicer to live with. Each would need a mockup and your sign-off before I touched anything.

  • 01Remember filters between visits The registry already persists column choices to localStorage, but search and filter selections reset on every visit — including the directory's new business-unit filter. Persisting them the same way would make the daily path shorter.
  • 02Give the empty states somewhere to go Most empty states state a fact ("No one matches that search"). Pairing each with the obvious next action — clear the filter, add the first employee, write the first announcement — turns a dead end into a step forward.
  • 03A confirmation step for money that can't be undone Committing medical locks for the plan year and only HR can change it, but it commits on a single button press. A short "here's what you're committing to, for the year" summary would fit the weight of the decision.
  • 04One toast pattern instead of three Employee benefits toasts appear bottom-left, admin ToastForm toasts elsewhere, and several screens still surface success through a redirect banner. Consolidating on one would make "did that save?" answerable at a glance anywhere in the app.
  • 05Loading feedback on the heavy screens The registry, directory and incentive report are all force-dynamic and can pause visibly on a slow connection with no skeleton or spinner. A loading state would stop them feeling stalled.
  • 06Make the sticky benefits header earn its space on mobile The page header is sticky top-0 and takes a real bite out of a phone screen while scrolling a long benefit list. Condensing it once scrolling starts would give the content back.
F1 and F2 are fixed and pushed. Fixing F1 also uncovered a defect this audit had missed: the flexible-claim amount input formatted its own value and parsed it back with /[^0-9]/g, so on an Arabic-locale browser every keystroke stripped the value — 1,234 + "5" became 5, and no claim above 9 EGP could be entered at all. That is fixed too, and every remaining money figure in the app and its server messages is now locale-pinned.

Everything else remains a proposal. F4, F5, F7, F8 and F9 are behavioural and could be fixed without changing how anything looks. F3 is mechanical and invisible. F6 is the only one that changes a layout, so it would get a mockup and your approval first — as would any of the six suggestions.
