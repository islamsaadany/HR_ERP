Employees registry — two ways it can scroll

Benefits Reporting now has the scroll-away header you approved. The registry cannot have both that and its frozen Name column — CSS will not let a box scroll sideways while its header sticks to the page. Scroll inside each frame; the choice is which one the registry (and the benefits catalogue, which has the same shape) should use.

Why it's either/or. Freezing the Name column needs the table to sit in a horizontally scrollable box. The moment a box scrolls in any direction the browser makes it a scroll container, and a sticky header inside it sticks to the box, not to the window — so the page title can no longer be what it parks under. Reporting escapes this only because its nine columns fit without sideways scrolling; the registry has twenty-two.

Scroll down: the title stays, the toolbar goes, the navy header parks under the title. Now scroll sideways — the Name column slides away, and so do the title and toolbar, because the page itself is what moves.

What you gain

  • Same behaviour as Benefits Reporting — one rule across the app
  • The toolbar and filters stop eating permanent screen height
  • The whole page scrolls, so there is never a second scrollbar to hunt for

What you lose

  • The Name column scrolls out of sight when you go sideways
  • With 22 columns on, you lose track of whose row you are editing
  • Inline editing a far-right cell means scrolling back to check the person
  • The whole page scrolls sideways — the title and toolbar slide off to the left too

What you keep

  • Name always visible, however far right you scroll
  • Safe inline editing across 22 columns

What stays imperfect

  • The title and toolbar keep their permanent screen height
  • Two scroll regions on the page rather than one
  • Registry and Reporting behave differently

My recommendation

Option B — leave the registry and the catalogue exactly as they are. The frozen Name column is worth more than scroll consistency on a table you inline-edit: losing track of whose row you are on is a data-entry error, while a slightly tall header is only an annoyance. The scroll-away treatment then applies to the tables that genuinely fit — Reporting today, and any narrow table we add later.

If you would rather have the consistency, say so and I will apply Option A to both. There is a third possibility if neither feels right: keep the frozen column and make the box taller by letting the toolbar scroll away above it — more work, and it still leaves two scrollbars, so I would not start there.
