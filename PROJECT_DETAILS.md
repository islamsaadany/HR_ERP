## 1. Product summary
An internal, English-language HR platform for **Forefront Consulting**. Email + password sign-in (Google parked), two roles (Employee, HR/Admin), and five v1 modules built on a shared employee registry.

## 2. Stack
| Layer | Choice |
|-------|--------|
| Framework | Next.js 15.5 (App Router) + React 19 · Tailwind v4 |
| Language | TypeScript |
| DB | PostgreSQL (Neon) + Prisma |
| Auth | NextAuth v5, email + password (Credentials); Google parked (env-gated) |
| Styling | Tailwind v4, **navy/gold** tokens on subtly warm neutrals; **Fraunces** (display) + **Hanken Grotesk** (body) self-hosted via `next/font`; soft card elevation + staggered reveals; gold keyboard focus rings |
| Files | Vercel Blob (**private** store; files streamed through authorized server routes, never by raw URL — see `src/lib/blob-serve.ts`) |
| Deploy | Vercel |
| Email | none (v1) |

### Why Next.js/Prisma/Postgres over the Firebase reference
The v1 modules that could be reused from the Firebase reference (directory, HR docs, dashboard, onboarding) are simple CRUD that port easily, while the module that was deeply Firebase-coupled (Learning Track) is deferred. The hardest v1 module — Benefits — involves money, admin-configured rules, and role checks, which are cleanest enforced server-side against a relational schema. Choosing the house stack also keeps HR_ERP consistent with Forefront's other products (Frost, Endurance) so future sessions bootstrap from the same conventions.

## 3. Modules → features → data (v1)

### Foundation (cross-cutting) — spec `001`
- Email + password sign-in (Google parked), app shell + left nav, My Profile, and **My Documents** (personal uploads).
- **Auth:** sign-in is email/password (NextAuth Credentials); any registered employee may sign in (domain lock lifted, HR warned on non-company emails). A bootstrap admin bridge (`BOOTSTRAP_ADMIN_*`) is retained as a fallback. Forced temp-password change on first login (see §3 Authentication).
- **Bulk employee import:** Admin → Employees → **Import CSV** uploads the HR spreadsheet (upsert by email; tolerant date parsing with day-first for ambiguous dates; tenure band derived from hire date; per-row review report). Replaces a hand-written PII SQL seed.
- **Export → edit → re-import round-trip:** Admin → Employees → **Export CSV** (`/api/admin/employees/export`) downloads all employees pre-filled in the exact import format (Name, Email, Department, Title, Contract Type, Date of Hiring, Phone, DOB, Marital Status, Manager Email, **Spouse Name, Spouse Date of Birth**, Number of Kids, **Kid N Name + Kid N Date of Birth**, **Emergency Contact Name / Relationship / Phone**). HR fixes blanks/mistakes and re-uploads to update everyone by email — the **spouse is a `Dependant kind=SPOUSE`** (needs a DOB so medical can price it), children carry names, and emergency contact round-trips. Round-trip verified (parses back with no errors). Role, status, and salary are intentionally NOT in the CSV (set in-app; import never overwrites them).
- Roles: `EMPLOYEE`, `HR_ADMIN`, `SUPER_USER` (superset). Manager is a capability derived from the org chart. Bootstrap via `ADMIN_EMAILS`; Super User promotes in-app.
- Registry fields (public: name, email, department, title, phone) + HR-private (employment type, tenure band, start/end date, status Active/Left, DOB, marital status, dependants {name, dob}, reportsTo, **emergency contact {name, relationship, phone}**). **Emergency contact** (migration `028`) is HR-managed — the three fields are **required on the admin employee form** (create + edit; validated server-side in `employeeSchema`) and shown **read-only** on the employee's own **Profile** ("Managed by HR"); it is deliberately **not** surfaced in the Team Directory. Columns are nullable, so pre-existing employees read "—" until HR edits them (the next save requires all three). **Monthly salary is confidential — Super-User-only** (HR Admin cannot see or edit it): the employee grid column, the create/edit form field, and inline edits are all gated to Super User (`canSeeSalary` in `lib/roles.ts`), and the salary is never sent to the client for HR Admin. The salary-driven **incentive** module is already Super-User-only, and CSV export/import exclude salary. Age / years-of-service / dependant ages are **derived, not stored**. Employees self-edit contact only. Monthly salary drives the Loans benefit ceiling (each employee sees their own). **Tenure band & status are derived, not entered:** the **tenure band** is auto-calculated from the **hire date** (`deriveTenureBand` in `src/lib/tenure.ts` — under 6 months = no band, then 6mo–2y / 2–4y / 4–7y / 7–10y, capped at the top band beyond 10y) and the **status** is driven entirely by the **end date** (an end date ⇒ **Left**, otherwise **Active** — `statusFromEndDate`). Both are **read-only** in the grid and shown as read-only derived displays on the create/edit form (the create/edit **Employment** section — reworked 2026-08-12 — leads with **Employment type + Monthly salary**, then **Start date + End date** side by side, then a grouped "Calculated from the start date" panel showing derived **Years of service** — `formatYearsOfService` in `src/lib/tenure.ts`, e.g. "3 years 4 months", counted to the end date if the employee has left — and **Tenure band**, then **Reports to + Role**; **status is no longer a field** but a green **● Active** / muted **● Left** badge in the section header, driven live by the end date); editing a **start date** recomputes the band and an **end date** recomputes the status, on both the client (instant) and the server (persisted on every create/edit/inline write). The registry always shows the current derived values. Existing rows are re-synced by the one-time backfill `prisma/sql/029_derive_tenure_status_backfill.sql` (⚠ flips any employee marked *Left* with no end date to *Active*). **Benefits derives tenure at read time:** the employee benefits module computes the band from the hire date wherever it matters — the display page (`benefits/page.tsx`), medical commit (`commitMedical` in `actions.ts`), and the **server-authoritative claim path** (`claim-actions.ts`, both the guaranteed band amount and the pool-ceiling enforcement) — via the same `deriveTenureBand`, so what the employee sees and what the server enforces always agree and never drift. The rule math in `rules.ts` is unchanged (only the band input is derived, mirroring how proration already derives eligibility from the start date). **Residual:** the admin guaranteed-benefit bulk **Release** sheet (`ReleaseManager`) and the Team Directory still read the **stored** columns; status stays correct (only changes via an end-date write), and the stored tenure band is kept in sync on every employee write + the 029 backfill, so its only drift is the release sheet showing a stale band until the record is re-saved. **Registry grid (`EmployeeGrid`):** the Admin → Employees table is inline-editable (click a cell), columns are drag-reorderable and toggleable, and **clicking the Name / Department / Type / Status / Start date / Monthly salary header sorts A→Z then Z→A** (view-only over the filtered rows, blanks first on ascending; caret ↑/↓ marks the active column). The registry list page renders **full-width** (see the shared table treatment below), so the many-column table fills the screen and inline edits no longer trigger a horizontal scrollbar.

- **Benefits — claim-based living allowance (spec `018`, migration `025`) — CURRENT MODEL, supersedes the basket descriptions below:** the flexible basket is replaced by a claim-as-you-go allowance. There is **no submit and no per-benefit allocation** — employees file `BenefitClaim`s directly against active catalog items any time the plan year is open, entering the **full price paid** (exact, no 1,000 rounding) while the server computes the **covered share** (`coverageRate%`). Server rules (`src/lib/benefits/rules.ts` → `evaluateClaim`): a **50%-of-pool cap per benefit** on cumulative covered claims (pending+released), now **full- and part-time**, and the **pool ceiling** across the committed medical premium + all covered claims. **Exceeding either limit clamps the payout rather than refusing the claim (2026-08-16, `clampCovered`)** — reimbursement is the smallest of the coverage share, the benefit's remainder, and the pool's remainder, so a 10,000 receipt at 80% with 7,000 left pays **7,000** (an effective 70%; the 50% cap overrides the coverage rate). The employee still enters the **full receipt value** — it has to match their proof — and the preview names the clamped figure before they submit. Only a **fully-used** benefit or pool refuses ("you've used the full 50% cap", "contact HR"). `BenefitClaim.fullCost` (migration `045`, nullable, no backfill) records the receipt alongside the covered `amount` so HR can reconcile a clamped claim against its proof on the admin Claims list. **Medical is the one commitment** — an employee `commitMedical`s once per plan year (a `MedicalCommitment` row: spouse/children → premium, capped at ceiling, 100% covered, 50%-exempt); after commit it's **locked to the employee, HR-editable only** (`editMedicalCommitment`/`removeMedicalCommitment` on the admin Submissions tab). The **benefit-count limit is removed** (kept as `COUNT_LIMIT_ENABLED=false` + `MAX_SELECT_*`). Data model: **`BenefitSelection` and `SelectionLine` are dropped**; `BenefitClaim` links to the catalog item directly. Cutover (`025`) is a **clean wipe** of selection data (test data); HR re-enters any real prior claims via manual entry (spec 016). UI: the Benefits page is a pool-summary + `MedicalCommitmentCard` + guaranteed band + `BenefitClaims` menu (the old `BenefitsSelector`/`BenefitsTabs` are removed); orientation + `/benefits/policy` rewritten to the new model; admin catalog rejects 0% coverage (1–100).
- **Unified catalogue — FT/PT eligibility & medical split (spec `021`, migration `032`):** the admin **Benefits Catalogue** tab now lists **every** benefit — guaranteed, flexible, and medical — in one table with a **Type** chip and two eligibility checkboxes, **FT** and **PT** (`GuaranteedBenefit.eligibleFullTime/eligiblePartTime` and the same pair on `BenefitCatalogItem`, toggled via `setEligibility`). An employee only sees benefits their employment type is eligible for (enforced server-side in `createClaim`/`commitMedical`, not just the UI). Guaranteed benefits are now **one row per benefit** (dropped `employmentType` + `band*`; added per-type `ftBand*`/`ptBand*`, still allowing different FT vs PT figures) — `amountForBand(employmentType, band, row)` picks the columns. The **Amounts** tab is now **numbers only** (pool ceilings, guaranteed FT/PT band grids, rate card); names/claim-requirements/eligibility moved to the Catalogue. **Medical is split** into two catalog items by `medicalScope` (`PERSONAL` = self, `FAMILY` = self + spouse + children); the employee's setup shows dependant pickers only when Family-eligible (a Personal-only employee sees self-cover with no spouse/children), and someone eligible for both gets a **single** section behaving like Family. `MedicalCommitment` is unchanged. Storage stays split (guaranteed vs catalog) — only the admin view is unified — so the money math is untouched. Migration `032` folds each guaranteed benefit's FT/PT sibling rows into one (repointing claims/releases), tags the existing medical item Personal, and adds the Family item; verified on a throwaway Postgres against the full chain. **Availability correction (2026-08-13):** an eligibility flag turns a benefit *on* for a type, but the per-type **band amount** can still be unset — e.g. **PT Summer allowance** (part-timers get no summer/loans, §5) or any figure HR hasn't entered. Such a benefit is now treated as **not available to that employee**: its card is **omitted** from the Benefits page and the orientation summary, and a claim is **blocked server-side** ("no amount set for you yet — contact HR"). Previously a null band amount fell back to the employee's **monthly salary** (`amountForBand(...) ?? user.monthlySalary`), which showed a **wrong figure and leaked salary** onto a benefit card and — worse — let the **server authorize a claim up to the salary** (a real over-claim risk, since benefits money is server-authoritative). The monthly-salary fallback now applies **only** to genuinely salary-driven benefits (**Loans** — all bands null, `isSalaryDriven`), guarded in `benefits/page.tsx` and `benefits/claim-actions.ts`. This matches what the bulk-release sheet already reported ("no part-time amount set").
- **Age-banded per-person medical rate card (spec `023`, migration `034`):** medical is priced **per covered person by age band**, replacing the old relationship-based card (`self`/`spouse`/`childUnder18`/`child18Plus`). A new **`MedicalRateBand`** table holds one row per age band (a `tier` column for future tiers — only **Tier 1** today; `annualPremium` is a two-decimal `Decimal`, seeded with the operator's 12 figures 3990.72 … 29796.12). An employee's premium = the **sum of each covered person's age-band annual premium** (employee + covered dependants), where each person's figure is **truncated to whole EGP (cents dropped, not rounded)** before summing; a mid-cycle joiner's premium is that annual × `months ÷ 12` (spec 019), also truncated, capped at the pool ceiling. **Age is measured at the commit date** and locked. Pricing lives in **`src/lib/benefits/rates.ts`** (`ageAt`/`bandFor`/`sumMedicalPremium`, pure) and is enforced in `commitMedical` (`benefits/actions.ts`) and the HR override `editMedicalCommitment` (`admin/benefits/actions.ts`). A **`MedicalCoveredPerson`** snapshot (one row per covered person: label, ageAtCommit, whole-EGP premium) is written at commit so the locked premium stays explainable and immune to later DOB edits. **DOB is required to commit** — the employee's DOB (else blocked with a message), and the **spouse becomes a `Dependant` (kind `SPOUSE`)** entered in the employee form's dependant list like children (a Child/Spouse **type** selector; one spouse max, server-enforced); the medical modal only **selects** which existing dependants to cover. Someone **over 75** is priced at the top band (70–75) and flagged for HR. Admin **Amounts** tab edits the 12 bands (`updateMedicalRateBand`, keeps the operator's cents). The old `MedicalRateCard` table + `computeMedicalPremium` are dropped; legacy `MedicalCommitment` count columns (`spouse`/`childrenUnder18`/`children18Plus`) are nullable and retained for historical rows only.
- **Cycle-length proration (spec `019`, revised 2026-08-11; migration `027`):** a plan year carries an admin-set **start/end window** (`PlanYear.startDate`/`endDate`, set via the **Plan year** dialog; end must be after start; blank = proration off). **Two distinct rules now apply** (the original release prorated everything only for mid-year *starters*; the pool/Prof-dev half was changed on 2026-08-11 to key off the **cycle length** so a short cycle scales the allowance for **everyone**):
  - **Flexible pool + guaranteed Professional development → scale to the CYCLE LENGTH.** The fraction is `cycle whole months ÷ 12` (whole calendar months the plan-year window spans — a full year → 12, a half-year 1 Jan–30 Jun → 6), applied to **every** eligible employee, existing staff and mid-cycle joiners alike (**no extra reduction** for joining part-way through the cycle — product decision 2026-08-11). Thresholds still gate *eligibility*: an employee under **6 months** of service is **not yet eligible** and gets **0** pool/Prof-dev. `src/lib/benefits/proration.ts` → `cycleWholeMonths`/`cycleFraction`/`poolCycleFraction`, enforced in `createClaim` (pool ceiling + Prof-dev allocation) and mirrored on `benefits/page.tsx` with a **“Prorated · N of 12 mo”** indicator reading *“This benefits cycle runs N of 12 months…”*.
  - **Medical → unchanged: mid-cycle-joiner proration only.** Medical unlocks at **3 months** and is prorated by `annual × remaining whole months ÷ 12` measured **from the employee's own 3-month eligibility date** to the plan-year end (`classifyEligibility`/`prorate`); existing staff pay the **full** premium regardless of cycle length. A sub-6-month employee sees a **medical-only** Benefits view (basket + guaranteed shown as “unlocks at 6 months”), ceiling/rate looked up at the **entry 6mo–2y tier** (`poolCeilingFor(type, null)`), premium prorated by the 3-month fraction.
  - **Not prorated:** Marriage/Summer/Special events/Loans (event/season gifts — `GuaranteedBenefit.prorated=false`; only Professional development is `true`). Missing window or missing employee start date → **fail-safe to full amounts** (+ an admin “proration off” warning). All server-authoritative; the client mirrors the figures for display only. **Medical is now priced by the age-banded Tier-1 rate card (spec `023`)** — the placeholder relationship-based card was replaced; medical proration keeps the ÷12 mid-joiner rule, only the annual figure it prorates now comes from the age table.
- **Benefits orientation tour (spec `017`, migration `024`):** a personalized, first-run, skippable, re-openable **stepped-cards** walkthrough (`BenefitsOrientation`) on the employee Benefits page. Four steps in the employee's own numbers: **(1)** type · band · pool ceiling · **(2)** their guaranteed benefits with band amounts (Loans salary-driven) · **(3)** how the flexible basket works (categories, up to 5 FT / 3 PT, enter cost → company covers a % that draws from the pool, you pay the rest) · **(4)** the rules (coverage 100/80/50; no single benefit's company share over half the pool, **medical exempt**; claims = request or proof of full spend → reimbursed the covered portion) with a link to `/benefits/policy`. It **auto-opens** only when the selector is available and the employee **hasn't submitted and hasn't seen it**; the **"How it works"** button re-opens it any time. A per-user `benefitsOrientationSeenAt` flag (set once via `markOrientationSeen`) stops the auto-open. Read-only explainer over existing page data — **no selector or money-rule change**; graceful when figures are missing.
- **Admin Benefits redesign (spec `016`):** `/admin/benefits` is now **three tabs** — **Submissions & Claims** (default, most-used) · **Benefits Catalogue** · **Amounts** (the old *Configuration* and *Claim requirements* tabs are dissolved into these). **Benefits Catalogue** is one table (Name · Category · Order · Claim requirement · Coverage %) with hide/show + add; it absorbs the per-catalog-item claim-requirement editing and the coverage-% control (spec 012). **Amounts** groups pool ceilings, guaranteed amounts, guaranteed claim-requirements, and the medical rate card. Every config table is **view-first** — read-only with an **Edit** toggle (shared `EditableSection`); tables toggle independently. **Save feedback (2026-08-13):** every **Amounts**-tab save form (pool ceilings, guaranteed FT/PT amounts, each medical rate-card row) is wrapped in `ToastForm` (`components/admin/ToastForm.tsx`) — the server action is unchanged, but on success a **green `ff-toast`** (matching the employee benefits-claim toast; bottom-left, auto-dismiss) confirms the write, and a **red** toast surfaces a failure instead of the previous silent submit. ### Employee ID + linked-account switching (spec 025, migration `040`)
- **For a person holding two contracts across two group companies** (kept as **two independent
  employee records with two distinct emails** — email stays the unique per-account login; the login
  model is unchanged). Adds **`User.employeeId`** — an HR-managed **person** identifier that is
  **optional and NOT unique**: the two records share the same Employee ID, and that shared value links
  them. Settable on the employee **form + grid + CSV** (like business unit).
- **Link confirm:** saving an Employee ID already used by another active record warns "this links the
  accounts as the same person" and requires ticking **Link accounts** on the form (`employeeIdLinkGuard`);
  the inline grid **blocks** a linking duplicate and points to the form (linking is deliberate).
- **Account switcher — password-less (spec `026`, 2026-08-15; supersedes the spec-025 password prompt):**
  when the signed-in user's Employee ID is shared with other **active** accounts, the sidebar shows
  **"Switch account"** listing them (name · business unit). Selecting one now moves them into that account
  **immediately, with no password** — the session they already hold is what authorises it. Two-stage and
  server-authoritative: `switchAccountAction` verifies the live session and the link, then mints a
  **60-second HMAC-signed ticket** (`src/lib/switch-account.ts`, `AUTH_SECRET`, no new env var); a dedicated
  **`switch-account` credentials provider** (`src/lib/auth.ts`) verifies that signature **and independently
  re-reads both employee records**, re-running the shared `isLinked` predicate before issuing a session —
  because its callback route is publicly POST-able, so nothing it receives is trusted. `isLinked` requires
  both records **ACTIVE**, the target ≠ the actor, and the **trimmed, non-empty** Employee IDs to match; the
  sidebar list is filtered through the **same predicate**, so what is offered can never exceed what is
  permitted (this also closed a latent gap where a **whitespace-only** Employee ID counted as a link).
  Everything **fails closed** — a bad ticket, an un-migrated DB, or any error refuses the switch.
  Impersonation is cleared **before** the ticket is minted and the switcher stays hidden while
  impersonating. The target's role is never inherited (the `jwt` callback re-resolves it from the DB each
  call) and the target's **forced password change still applies** on arrival. **Session lifetime is
  unchanged** (NextAuth default 30 days) — reviewed and deliberately kept. **No migration.** Verified by
  `scripts/verify-switch-account.mts` against a throwaway Postgres (**27/27** — forged ticket, expired
  ticket, unlinked target, LEFT target, and a link revoked *after* the ticket was minted, all refused).
  ⚠️ **Accepted residual risk:** the Employee ID is HR-typed and non-unique, so a **mistyped ID links two

  *Residual Risks*. No simultaneous multi-session, no password-less hop, never lists an

  brand/benefits/data). Interim toward spec 022's "one identity, many employments". Verified on a

### Authentication — email + password (Google parked)
- Sign-in is **email + password** (NextAuth Credentials), matching the employee by email. `User.passwordHash` (scrypt via Node crypto, no dependency; migration `014`). **Google sign-in is disabled for now** — the button is removed from the sign-in page; the provider is still env-gated (`AUTH_GOOGLE_ID`/`_SECRET`) so it can return later. Bootstrap admin bridge retained as a fallback.
- **Any registered email may sign in** — the company-domain restriction was **lifted** from password login (decision 2026-08-07). HR sees a **non-blocking warning** when creating an employee whose email isn't on `ALLOWED_EMAIL_DOMAIN`. (The dormant Google `signIn` callback still domain-checks, but Google is off.)
- **Forced temp-password change (migration `021`, `mustChangePassword`):** any admin-issued password — a single set/reset **or** the bulk generator — is temporary. On next sign-in the employee is gated to **`/set-password`** (a standalone page outside the `(app)` shell, so no redirect loop) and cannot reach the app until they choose their own. The flag clears when they set a compliant password (there or on Profile).
- **Password policy** (`validatePasswordPolicy`, server-enforced on `/set-password` and Profile; mirrored in the UI): **≥ 8 chars, an uppercase letter, a number, and a special character**. Temporary passwords are exempt (they force a compliant change).
- **HR bulk temp passwords:** Admin → Employees → **Passwords ▾** menu (`RegistryHeader`) → `generateTeamPasswords`, in three modes:
  - `missing` — "Generate for employees without a password".
  - `selected` — "Reset selected employees…" opens `ResetSelectedPasswordsModal`, a searchable checkbox picker of ACTIVE employees (each row chipped **Has password** / **No password yet**); the ticked ids post as `ids`. Any admin may run it — it is N single resets, which HR could already do one at a time.
  - `all` — "Reset ALL passwords", **Super User only**.

  In **every** mode the acting admin is excluded server-side (no self-lockout) and the population is intersected with `status: ACTIVE`, so a tampered `ids` list can't widen the blast radius. Plaintext is returned **once** as a **one-time CSV** (name · email · password) — stored only as scrypt hashes, never re-shown. **No emails in v1**, so a forgotten password is reset the same way (no self-service recovery).

## 5. Benefits domain model (real policy from the Onboarding Kit; interaction ported from the HTML simulator)
- **Employment type:** Full-time / Part-time.
- **Tenure bands (confirmed):** 6mo–2y · 2–4y · 4–7y · 7–10y.
- **Pool ceiling (confirmed, EGP):** FT 20,000 / 30,000 / 45,000 / 65,000 · PT 14,000 / 21,000 / 30,000 / 42,000. (Note: real PT is ~65–70% of FT, not the policy's "50%" wording.)
- **Fixed / guaranteed benefits:** Marriage allowance · Loans (after 1yr, 1-month salary) · Summer allowance · Professional development · Special events. Shown first, separate from the basket. **Professional development is covered at 100% of cost, up to the tenure-band allowance** (decision 2026-08-09, migration `026`) — previously framed as 50%; the per-band amounts are unchanged, only the coverage framing (the employee claims the full cost up to the allowance, with proof).
- **Flexible basket:** catalog grouped into 5 display categories (ported from `benefitsselector_3.html`) — **Health & protection** (Personal medical insurance, Annual health check-up) · **Wellbeing** (Gym, Coaching / therapy, Sports) · **Life & family** (Schooling / education, Childcare / nursery, Caregiver support) · **Personal growth** (Personal learning) · **Lifestyle & flexibility** (Mobile device, Home-office setup). Personal medical insurance covers the employee only; spouse/children are separate priced options in the medical modal. FT: no single benefit's **company share** > 50% of the pool (⇒ practically ≥2 picks), **max 5** picks. PT: **max 3** picks, exempt from the 50% cap. Costs in steps of 1,000. Catalog rows carry a `category` field.
- **Company coverage rates (spec `012`, migration `023`):** each flexible benefit carries a **`coverageRate`** (percent). The employee enters the benefit's **full cost**; the **covered (company) share = cost × rate/100** is the only part that draws from the pool, and the employee pays the remainder (out-of-pocket). **All money rules run on the covered amount** — pool total, over-pool, and the FT 50% single-benefit cap. Seeded rates: **100%** — Personal medical, Annual check-up, Coaching · **80%** — Gym, Sports, Schooling, Childcare, Caregiver, Personal learning · **50%** — Mobile, Home-office. Medical stays a single **100%-covered** rate-card item (cost = covered = premium), cap-exempt. `SelectionLine` stores both `cost` (entered) and `amount` (= covered pool draw); pre-012 rows backfilled `cost = amount`. The math lives in `src/lib/benefits/coverage.ts` (shared by the server rules and the client selector). The selector shows **cost · company share · your share** per benefit and the meter tracks the **company share**; claims reimburse the **covered portion** against proof of full spend. HR edits the rate per benefit in the admin Benefits **Configuration** catalog editor. Server-authoritative (`src/lib/benefits/rules.ts` + `saveBasket`).
- **Guaranteed amounts (confirmed, EGP by band):** FT — Marriage 18/24/30/36k · Summer 2.5/3.5/5/6k · Prof-Dev 5/9.5/18/21.5k · Special events 6/8.5/12/18k · Loans = 1-month salary from yr 1. PT — Marriage 9/12/15/18k · Prof-Dev 5/7/9/11k · Special events 6/8.5/12/18k (no summer/loans).
- **Medical insurance (confirmed):** single tier — self 8,000 (always included), spouse 8,000, child <18 4,500, child ≥18 8,000; **exempt from the 50% cap**, capped at the pool ceiling; dependants entered manually for now.
- **Claims/reimbursement:** Phase 2 (v1 ends at a submitted, locked selection).
